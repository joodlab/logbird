## Restore-specific failure and remediation

[Issue75](https://github.com/joodlab/logbird/issues/75) records the exact reproduction. Immediately after native restore, with worker/server/app stopped: raw=minute10002, entities actual=expected30000, attributes actual=expected20000. Thus restore did not fire MVs. After failed-run repair: raw10002, minute20004, entities60000, attributes40000, despite a completed receipt.

Restored parts retained data_version405/1204/410. Fresh full-project delete mutations2/3 reported done with empty failure reasons while old rows stayed visible. Administrator grants and synchronous delete settings were correct. A fresh-no-restore controlled failure/retry passed, isolating the problem to restored parts.

The source fix verifies raw and scoped/full rollup deletion before reinserting, and throws `LOGBIRD_DELETE_INCOMPLETE` if visible rows remain. Five regression cases prove no insert occurs after an ineffective delete. This guard still needs a live restored-data test and Docker rebuild.

The explicit operator normalization SQL stages visible raw rows on disk, checks equality using EXCEPT ALL in both directions, truncates raw plus rollups and replays raw rows through existing MVs once. Live execution returned zero for all seven checks: two stage comparisons, two replay comparisons and three independent aggregate invariants. This compares every selected raw column, preserving received_at and payload exactly. The newer outstanding-mutation precondition and read-only dry-run file still need the next live run. The script never runs automatically and preserves staging for recovery.

Migration006 / [PR62](https://github.com/joodlab/logbird/pull/62) adds event_ids/event_ids_mv. Normalization includes TRUNCATE TABLE IF EXISTS event_ids, but that schema was not present during this proof. Receipt uniqueness after006 is a remaining recovery gate. Custom MVs require operator review of all destinations before replay.
