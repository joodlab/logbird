# Self-hosting

## Five-minute quickstart

Install Docker Engine and Compose >=2.24.4 (Linux containers). First builds can take longer depending on CPU/network. No images are published yet.

```sh
git clone https://github.com/joodlab/logbird.git
cd logbird
sh scripts/selfhost-init.sh
# Configure SMTP in .env, or explicitly set AUTH_LOG_SIGN_IN_CODES=true.
docker compose up -d
```

Open http://localhost:4600. Enter your email; read the code in your inbox, or privately run `docker compose logs server` when the log fallback is enabled. Create a workspace and project, copy its ingest key (shown once), then send:

```sh
export LOGBIRD_INGEST_KEY=lb_ingest_...
curl http://localhost:4600/v1/events -H "Authorization: Bearer $LOGBIRD_INGEST_KEY" -H 'Content-Type: application/json' -d '{"action":"document.updated"}'
```

Expect HTTP 202 and the event in Explorer. Only action is required. Never send secrets. `/livez` checks the API process; `/readyz` checks Postgres, ClickHouse and Redis through the app.

Init supports POSIX sh on Linux/macOS/Git Bash, creates .env if absent, fills only empty/missing secrets, preserves populated values and sets mode 600. Manual generation: `openssl rand -hex 32`, then paste privately into .env. Init falls back to /dev/urandom without OpenSSL. Never commit credentials.

## Environment reference

One .env.example serves source development and containers. Empty URL overrides let Compose construct internal URLs. Existing contributor files keep working. Source development must set DATABASE_URL, CLICKHOUSE_URL and REDIS_URL to host services; Mailpit uses SMTP_HOST=127.0.0.1 and SMTP_PORT=1025. Container localhost refers to itself.

| Key | Requirement / default |
| --- | --- |
| BETTER_AUTH_SECRET | Required, >=32 characters; init generates 64 hex characters |
| POSTGRES_PASSWORD, CLICKHOUSE_PASSWORD | Required; generated by init |
| CLICKHOUSE_QUERY_PASSWORD | Required, 64 lowercase hex characters; must authenticate existing user, never rotated |
| CLICKHOUSE_QUERY_USER | Fixed logbird_query for provisioning |
| APP_URL | Public origin, http://localhost:4600; HTTPS required except localhost/127.0.0.1 |
| POSTGRES_USER / POSTGRES_DB | logbird / logbird |
| DATABASE_URL | Optional complete URL; otherwise composed from credentials |
| CLICKHOUSE_URL / CLICKHOUSE_USER / CLICKHOUSE_DATABASE | http://clickhouse:8123 / logbird / logbird; keep database logbird because restricted policies name it explicitly |
| REDIS_URL / BULLMQ_PREFIX | redis://redis:6379/0 / {logbird} |

URL-encode special characters in manual connection URLs. Generated hex values need no encoding. .env.example preserves optional BASE_URL, SMOKE_* and LOGBIRD_*_KEY smoke inputs. No automated image builds or registry pushes run.

## SMTP and first login

Configure SMTP_HOST, SMTP_PORT, SMTP_SECURE, SMTP_USER, SMTP_PASSWORD and MAIL_FROM using provider settings. Examples: Amazon SES regional SMTP endpoint and SMTP credentials; Postmark smtp.postmarkapp.com:587 and server token credentials; Brevo smtp-relay.brevo.com:587 and SMTP credentials. Verify sender/domain and SPF/DKIM/DMARC with the provider.

Without SMTP explicitly enable AUTH_LOG_SIGN_IN_CODES=true. Each auth.sign_in_code JSON line contains recipient/code: log readers can sign in. Only sign-in bypasses SMTP, never invitations or other OTP purposes. With SMTP configured it logs and sends. After SMTP works, disable the flag and run `docker compose up -d server worker`; handle existing log retention appropriately. Missing SMTP with the flag off fails delivery. Invitations/courtesy emails need SMTP.

## Caddy TLS

Point DNS to the host and allow 80/443. Set APP_URL=https://audit.example.com, LOGBIRD_DOMAIN=audit.example.com, optional ACME_EMAIL, and TRUST_PROXY=2 (Caddy plus the console). Run `docker compose --profile tls up -d`. Pinned Caddy 2 uses the committed Caddyfile, automatic HTTPS and persistent caddy_data/caddy_config volumes.

Set TRUST_PROXY explicitly: profiles cannot change another service's environment. Local TLS tests can mount a Caddyfile with `tls internal`, choose LOGBIRD_TLS_HTTP_PORT / LOGBIRD_TLS_HTTPS_PORT, and run `curl -k --resolve hostname:port:127.0.0.1 https://hostname:port/readyz`. Internal test certificates are not publicly trusted.

## Any reverse proxy

Forward the whole origin to port 4600, including /api, /v1 and readiness. The runtime app proxy retains CSP/security headers. Set APP_URL to the exact public HTTPS origin. Client addresses drive per-client rate limits, audit context and the sign-in email's "requested from" line. The console is always one trusted hop: it appends the address it received the request from to X-Forwarded-For. Keep the default TRUST_PROXY=1 when browsers and SDKs reach port 4600 directly. Set TRUST_PROXY=2 behind exactly one reverse proxy that appends the real client address (Caddy, Nginx `$proxy_add_x_forwarded_for` or `$remote_addr`, Traefik, Coolify), and add one per additional trusted proxy. Logbird reads the X-Forwarded-For entry that many places from the right, so entries a client sends are ignored. A count that is too high lets clients choose their own address; too low groups everyone under the proxy's address. Never expose server:4601.

Nginx inside an existing TLS server block (configure certificates separately):

```nginx
location / {
    proxy_pass http://127.0.0.1:4600;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_buffering off;
    proxy_read_timeout 300s;
}
add_header Strict-Transport-Security "max-age=31536000" always;
add_header X-Content-Type-Options nosniff always;
add_header Referrer-Policy strict-origin-when-cross-origin always;
```

Traefik labels on app (attach app to the proxy network and configure its letsencrypt resolver):

```yaml
labels:
  - traefik.enable=true
  - traefik.http.routers.logbird.rule=Host(`audit.example.com`)
  - traefik.http.routers.logbird.entrypoints=websecure
  - traefik.http.routers.logbird.tls.certresolver=letsencrypt
  - traefik.http.services.logbird.loadbalancer.server.port=4600
```

Keep forwardedHeaders.insecure disabled; trust only known upstreams. Live tail polls HTTP; no WebSocket/SSE. Exports stream: disable buffering and allow sufficient read timeouts.

## External services

Set DATABASE_URL, CLICKHOUSE_URL, REDIS_URL and ClickHouse admin/query credentials, then run `docker compose -f docker-compose.yml -f docker-compose.external.yml up -d`. The override uses !reset to remove bundled services and migration dependencies; use Compose >=2.24.4 ([Docker merge reference](https://docs.docker.com/reference/compose-file/merge/)). Base secret validation still applies, including POSTGRES_PASSWORD (unused with DATABASE_URL). External services must already be reachable/ready. Create the logbird ClickHouse database first.

Postgres needs schema migration rights. ClickHouse needs logbird schema/table/view DDL and read/write, CREATE/ALTER USER, CREATE/ALTER SETTINGS PROFILE, CREATE/ALTER ROW POLICY, SELECT WITH GRANT OPTION on the four Logbird tables, SHOW ACCESS/GRANTS and system.users/settings visibility. Use ClickHouse 26.9 with SQL_ settings. Provisioning checks credentials, four SELECT grants, effective limits and unchanged main-user row counts. Stop writes during upgrades; concurrent ingest can fail that safety check.

Redis 7 is default. Dragonfly requires `--cluster_mode=emulated --lock_on_hashtags=true`, matching brace-enclosed BullMQ prefixes such as {logbird} across producers/workers, and no queue eviction. Do not use ioredis keyPrefix.

## Upgrades and backups

Back up first, stop writes and pin a tested Git revision (image tags/digests when published). Stop existing server/worker before upgrading, then `docker compose up -d --build`. One-shot migrate gates new server/worker startup; failure blocks startup. Prisma/ClickHouse apply only unapplied migrations; query credentials stay unchanged. Initialization variables do not rotate stored database passwords. Preserve the original env securely with backups.

```sh
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > logbird.pg.dump
# Restore into an empty prepared database while writers are stopped.
cat logbird.pg.dump | docker compose exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner'
```

For ClickHouse BACKUP, mount this at /etc/clickhouse-server/config.d/backups.xml and durable storage at /backups, then recreate your ClickHouse container in a maintenance window:

```xml
<clickhouse>
  <storage_configuration><disks><backups><type>local</type><path>/backups/</path></backups></disks></storage_configuration>
  <backups><allowed_disk>backups</allowed_disk><allowed_path>/backups/</allowed_path></backups>
</clickhouse>
```

Run with an authenticated client; supply credentials privately:

```sql
BACKUP DATABASE logbird TO Disk('backups', 'logbird-2026-11-05.zip');
RESTORE DATABASE logbird FROM Disk('backups', 'logbird-2026-11-05.zip');
-- File('/backups/logbird-2026-11-05.zip') also works with allowed_path.
-- S3 alternative, scoped credentials supplied privately, not in shell history:
-- BACKUP DATABASE logbird TO S3('https://bucket.s3.region.amazonaws.com/path/backup', '<access-key>', '<secret>');
-- RESTORE DATABASE logbird FROM S3('https://bucket.s3.region.amazonaws.com/path/backup', '<access-key>', '<secret>');
```

Restore into isolated empty storage first and verify counts/application reads. Preserve ClickHouse access storage and query credentials, or reprovision before acceptance; database backup alone does not replace access configuration. Redis uses AOF: back up its volume consistently while stopped or follow its backup procedure. Keep matched backups off-host. `docker compose down` preserves volumes; `down -v` permanently deletes them.

## Sizing

Start a bounded evaluation with 4 vCPU, 8 GB RAM and SSD. This is an initial allocation, not measured capacity. Reserve RAM/disk for ClickHouse merges/backups and measure compressed growth with fictional representative traffic. Monitor disk, readiness, 5xx/429, queue age, retention failures and backup age. One VM has no HA. See [deployment](deployment.md) and [Coolify](coolify.md).

## Upgrading from the previous namespace

Existing installations need an explicit, offline namespace migration before running
this version. Do not point the new code at empty databases beside existing data.
The script requires the old administrator connection settings and reuses
`CLICKHOUSE_QUERY_PASSWORD`; it never generates or prints replacement credentials.
Use `MIGRATION_DATABASE_URL` for a PostgreSQL administrator distinct from the old
application role (connected to `postgres`). PostgreSQL cannot rename the session
user. A database rename requires every other connection to be closed; the script
lists blockers and refuses rather than terminating them.

1. Stop ingress, console, server, workers and every other database client, including
   development worktrees. Drain in-flight jobs. Take PostgreSQL `pg_dump` plus globals,
   a ClickHouse backup including access metadata, and a Redis snapshot; verify restore
   into a separate instance. Preserve `.env`, passwords and the migration journal.
2. From the repository root with the old `.env` still in place:

   ```sh
   node --env-file=.env --import tsx scripts/migrate-namespace-to-logbird.ts --dry-run
   node --env-file=.env --import tsx scripts/migrate-namespace-to-logbird.ts --yes
   ```

   `--include-local-fixtures` opts into changing only fixture email suffixes.
   `--drop-old-redis-keys` opts into scanning/deleting only the exact old queue prefix.
   Omit both by default. No Redis flush is used. The dry run inspects prerequisites
   and prints the plan without writes. `.tmp/namespace-migration.json` records object
   definitions and pre-move physical table counts; keep it with the backups. On
   interrupted runs, retain that journal and rerun with all writers still stopped.
   The completed journal is archived with a `.completed` suffix. Materialized views
   are moved and rebound from their captured definitions; their destination tables
   carry the verified row counts. Source payload JSON remains original audit evidence.
3. Apply the printed environment name changes. Set Postgres database/user to `logbird`,
   ClickHouse database to `logbird`, restricted user to `logbird_query`, queue prefix
   to `{logbird}`, and rename branded environment keys to `LOGBIRD_*`. Keep passwords.
   A server-configured ClickHouse administrator (XML/environment configuration) must
   be renamed in that configuration using the same password; the migration does not
   rewrite server configuration. SQL access objects for restricted reads are rebuilt
   by the shared provisioning helper, then old policies/user/profile are removed.
4. Start database services with the updated identity configuration, deploy schema
   migrations, then start the Logbird server, worker and console. Confirm old stored
   API keys still ingest, new keys start with `lb_`, projects/users/events and derived
   counts match, cross-project reads remain denied, and retention completes on the new
   queue. Users sign in again; browser preferences start fresh.

If an in-place PostgreSQL rename is unavailable, restore `pg_dump` into `logbird`
using a separately provisioned `logbird` role with the existing password and ownership.
Verify counts, constraints, sequences and stored API-key hashes before switching;
keep the original database offline as recovery until acceptance. Do not run the
rename tool against two populated PostgreSQL namespaces. On failure keep writes
stopped and investigate with the journal; recover all three stores from the same
backup boundary rather than mixing old and new writes. The script is offline and
idempotent, not a distributed transaction or an online migration.
