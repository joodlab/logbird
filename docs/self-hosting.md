# Self-hosting

## Five-minute quickstart

Install Docker Engine and Compose >=2.24.4 (Linux containers). The default stack
pulls the four published GHCR images for `LOGBIRD_VERSION=0.1.1`; it does not
compile source. Images are available only after the corresponding tagged release
finishes publishing. Check the [release page](https://github.com/joodlab/logbird/releases)
before installing; release preparation in Git is not proof of registry availability.

```sh
git clone --branch v0.1.1 https://github.com/joodlab/logbird.git
cd logbird
sh scripts/selfhost-init.sh
# Configure SMTP in .env, or explicitly set AUTH_LOG_SIGN_IN_CODES=true.
# For an internet-facing instance, set AUTH_SIGNUP=restricted and AUTH_SIGNUP_DOMAINS.
docker compose pull
docker compose up -d --no-build
```

Set `LOGBIRD_VERSION` to an exact released version, without the leading `v`.
Role names are `ghcr.io/joodlab/logbird-<role>:<version>`. Compose uses
`pull_policy: always`; the normal startup path pulls images, and a missing or
private package fails clearly. All four GHCR packages must be public for anonymous
pulls. Maintainers configure this after first publication; see [releases](releases.md).
For a mirror, set `LOGBIRD_IMAGE_REGISTRY` to its namespace.

### Build from source

For unreleased code or a customized build, add the explicit override on every
build/start command. It uses separate `logbird-source/<role>:local` names and
`pull_policy: build`, keeping local builds separate from published versions.

```sh
git clone https://github.com/joodlab/logbird.git
cd logbird
sh scripts/selfhost-init.sh
# Configure SMTP/signup as above. Build sequentially to limit peak memory.
docker compose -f docker-compose.yml -f docker-compose.build.yml build migrate
docker compose -f docker-compose.yml -f docker-compose.build.yml build server
docker compose -f docker-compose.yml -f docker-compose.build.yml build worker
docker compose -f docker-compose.yml -f docker-compose.build.yml build app
docker compose -f docker-compose.yml -f docker-compose.build.yml up -d --no-build
```

Keep the override flags for later source-install operations. First builds need
more CPU/RAM/cache storage than runtime. Build stages default to one pnpm task
and four downloads (`BUILD_CONCURRENCY=1`, `DOWNLOAD_CONCURRENCY=4`). You may add
`--build-arg NODE_OPTIONS=--max-old-space-size=1536` to each build; this limits each
Node heap, not total Docker VM memory. On Windows use a current Docker Desktop
Compose version. Existing registry settings are preserved by init; clear the old
`LOGBIRD_IMAGE_REGISTRY=logbird` value to use GHCR.

Open http://localhost:4600. Enter your email; read the code in your inbox, or privately run `docker compose logs server` when the log fallback is enabled. Create a workspace and project, copy its ingest key (shown once).

There is no separate instance-admin bootstrap account. A verified first login creates
a user, and creating a workspace makes that user its owner. Email sign-up defaults to open; set AUTH_SIGNUP=restricted and configure approved domains before exposing SMTP publicly:
the first user does not acquire authority over other workspaces. Keep the listener
private during evaluation; restrict ingress if the installation is intended only
for your team.

```sh
export LOGBIRD_INGEST_KEY=lb_ingest_...
curl http://localhost:4600/v1/events -H "Authorization: Bearer $LOGBIRD_INGEST_KEY" -H 'Content-Type: application/json' -d '{"action":"document.updated"}'
```

Expect HTTP 202 and the event in Explorer. Only action is required. Never send secrets. `/livez` checks the API process; `/readyz` checks Postgres, ClickHouse and Redis through the app.

Init supports POSIX sh on Linux/macOS/Git Bash, creates .env if absent, fills only empty/missing secrets, preserves populated values and sets mode 600. Manual generation: `openssl rand -hex 32`, then paste privately into .env. Init falls back to /dev/urandom without OpenSSL. Never commit credentials.

## SMTP and first login

Configure SMTP_HOST, SMTP_PORT, SMTP_SECURE, SMTP_REQUIRE_TLS, SMTP_USER, SMTP_PASSWORD and MAIL_FROM using provider settings. Examples: Amazon SES regional SMTP endpoint and SMTP credentials; Postmark smtp.postmarkapp.com:587 and server token credentials; Brevo smtp-relay.brevo.com:587 and SMTP credentials. Verify sender/domain and SPF/DKIM/DMARC with the provider.

Choose the TLS mode explicitly. On port 587 set `SMTP_REQUIRE_TLS=true` (with `SMTP_SECURE=false`): the server must
offer STARTTLS and the certificate must verify before credentials or a message are sent, otherwise delivery fails
with `ETLS` and nothing is sent. With `SMTP_SECURE=true` (implicit TLS, usually 465) TLS starts on connect. With
neither, STARTTLS is opportunistic and a downgraded connection can expose credentials and codes; the server logs
`email.smtp_tls_not_required` at boot for a non-loopback host. Certificate verification is never
disabled.

Postmark (the hosted instance's provider, [architecture decision](decisions.md)):

```sh
SMTP_HOST=smtp.postmarkapp.com
SMTP_PORT=587            # 2525 also offers STARTTLS where 587 is blocked
SMTP_SECURE=false
SMTP_REQUIRE_TLS=true
SMTP_USER=<server API token>     # the same token is both user and password
SMTP_PASSWORD=<server API token>
MAIL_FROM=Logbird <hello@notify.example.test>   # a verified sender signature or domain
```

Keep the token private (never in Git, tickets or logs); it can send as any verified sender of that Postmark server.
Logbird's messages are transactional and go to the server's default transactional stream; do not route them
through a broadcast stream. Align SPF/DKIM/DMARC, the return-path and bounce/suppression handling as described in
[transactional email](transactional-email.md#postmark).

Without SMTP explicitly enable AUTH_LOG_SIGN_IN_CODES=true. Each auth.sign_in_code JSON line contains recipient/code: log readers can sign in. Only sign-in bypasses SMTP, never invitations or other OTP purposes. With SMTP configured it logs and sends. After SMTP works, disable the flag and run `docker compose up -d --no-build server worker` using the selected images; handle existing log retention appropriately. Missing SMTP with the flag off fails delivery. Invitations/courtesy emails need SMTP.

For a Docker Desktop evaluation using an existing host Mailpit, set
`SMTP_HOST=host.docker.internal`, `SMTP_PORT=1025`, `SMTP_SECURE=false`,
`SMTP_REQUIRE_TLS=false` (Mailpit offers no STARTTLS), and leave
SMTP credentials empty. The server then logs `email.smtp_tls_not_required` at boot
(`host.docker.internal` is not loopback); that warning is expected for this local
sink only. Read the fictional recipient's message at
http://127.0.0.1:8025. Do not set container SMTP_HOST to 127.0.0.1. On Linux,
configure a reachable SMTP host (or an explicit host-gateway mapping); Docker
Engine does not universally provide the Docker Desktop hostname.

## Caddy TLS

Point DNS to the host and allow 80/443. Set APP_URL=https://audit.example.com, LOGBIRD_DOMAIN=audit.example.com, optional ACME_EMAIL, and TRUST_PROXY=2 (Caddy plus the console). Run `docker compose --profile tls up -d --no-build` with the selected release images (include the build override for source installs). Pinned Caddy 2 uses the committed Caddyfile, automatic HTTPS and persistent caddy_data/caddy_config volumes.

Set TRUST_PROXY explicitly: profiles cannot change another service's environment. Local TLS tests can mount a Caddyfile with `tls internal`, choose LOGBIRD_TLS_HTTP_PORT / LOGBIRD_TLS_HTTPS_PORT, and run `curl -k --resolve hostname:port:127.0.0.1 https://hostname:port/readyz`. Internal test certificates are not publicly trusted.

For a local-only test without DNS changes, set `APP_URL=https://audit.logbird.test:4743`,
`LOGBIRD_DOMAIN=audit.logbird.test`, `LOGBIRD_TLS_HTTP_PORT=4780`,
`LOGBIRD_TLS_HTTPS_PORT=4743`, and `TRUST_PROXY=2` in the private env file. Create
`.tmp/Caddyfile.local` (create `.tmp/` first):

```caddyfile
audit.logbird.test {
  tls internal
  reverse_proxy app:4600
}
```

Create `.tmp/compose.tls-local.yml` (both files are ignored):

```yaml
services:
  caddy:
    volumes:
      - ./.tmp/Caddyfile.local:/etc/caddy/Caddyfile:ro
```

```sh
docker compose -f docker-compose.yml -f .tmp/compose.tls-local.yml --profile tls up -d --no-build
curl --insecure --resolve audit.logbird.test:4743:127.0.0.1 https://audit.logbird.test:4743/readyz
```

Require HTTP 200 and inspect Caddy's issuance logs. `--insecure` is only for this
disposable local-CA check; normal clients must trust the issued CA or use public
certificates. The custom HTTPS port is in APP_URL so authentication's origin checks
match it. Port 4780 redirects to standard HTTPS; use the explicit 4743 URL for this
test. Revert local overrides before following the public ACME instructions.

## Any reverse proxy

Forward the whole origin to port 4600, including /api, /v1, readiness and the [API reference](#api-reference). The runtime app proxy retains CSP/security headers. Set APP_URL to the exact public HTTPS origin. Client addresses drive per-client rate limits, audit context and the sign-in email's "requested from" line. The console is always one trusted hop: it appends the address it received the request from to X-Forwarded-For. Keep the default TRUST_PROXY=1 when browsers and SDKs reach port 4600 directly. Set TRUST_PROXY=2 behind exactly one reverse proxy that appends the real client address (Caddy, Nginx `$proxy_add_x_forwarded_for` or `$remote_addr`, Traefik, Coolify), and add one per additional trusted proxy. Logbird reads the X-Forwarded-For entry that many places from the right, so entries a client sends are ignored. A count that is too high lets clients choose their own address; too low groups everyone under the proxy's address. Never expose server:4601.

Nginx inside an existing TLS server block (configure certificates separately):

```nginx
location / {
    proxy_pass http://127.0.0.1:4600;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_buffering off;
    proxy_read_timeout 300s;
}
add_header Strict-Transport-Security "max-age=31536000" always;
add_header X-Content-Type-Options nosniff always;
add_header Referrer-Policy strict-origin-when-cross-origin always;
```

Traefik labels on app (attach app to the proxy network and configure its letsencrypt resolver):

```yaml
labels:
  - traefik.enable=true
  - traefik.http.routers.logbird.rule=Host(`audit.example.com`)
  - traefik.http.routers.logbird.entrypoints=websecure
  - traefik.http.routers.logbird.tls.certresolver=letsencrypt
  - traefik.http.services.logbird.loadbalancer.server.port=4600
```

Keep forwardedHeaders.insecure disabled; trust only known upstreams. Live tail polls HTTP; no WebSocket/SSE. Exports stream: disable buffering and allow sufficient read timeouts.

## API reference

The console (public origin) forwards exactly these API-listener paths: `/api/*`, `/v1/*`, `/health`, `/livez`,
`/readyz`, and the read-only, unauthenticated `GET /docs` (interactive Scalar reference) and `GET /openapi.json`
(OpenAPI document). Every other path is served by the console itself, so no other server route becomes public
([architecture decision](decisions.md), #61). The allowlist lives in `apps/app/server/proxy-paths.ts`. The two reference
paths accept only GET and HEAD (the console answers other methods with `405`, `Allow: GET, HEAD`) and are forwarded
without `Cookie`, `Authorization` or `Proxy-Authorization`, so a signed-in browser's session never reaches the API
through them. `/api` and `/v1` keep their normal authenticated forwarding.

```sh
curl -I https://audit.example.com/docs          # 200 text/html
curl -I https://audit.example.com/openapi.json  # 200 application/json
```

The document's `servers` entry is `APP_URL`, so "try it" requests go to the public origin. The reference page loads
a version-pinned Scalar bundle from `cdn.jsdelivr.net` with Subresource Integrity; Scalar telemetry, hosted fonts and
its hosted AI agent are off. A `/docs`-only CSP allows exactly that bundle URL and Scalar's inline init script (by
hash) as scripts, and only same-origin requests.
Browsers without access to jsDelivr see an empty reference page; `/openapi.json` still works. To keep the reference
private, block `/docs` and `/openapi.json` at your reverse proxy.

## External services

Set DATABASE_URL, CLICKHOUSE_URL, REDIS_URL and ClickHouse admin/query credentials, select a released LOGBIRD_VERSION (or include the source-build override and build sequentially), then run `docker compose -f docker-compose.yml -f docker-compose.external.yml up -d --no-build`. The override uses !reset to remove bundled services and migration dependencies; use Compose >=2.24.4 ([Docker merge reference](https://docs.docker.com/reference/compose-file/merge/)). Base secret validation still applies, including POSTGRES_PASSWORD (unused with DATABASE_URL). External services must already be reachable/ready. Create the logbird ClickHouse database first.

Postgres needs schema migration rights. ClickHouse needs logbird schema/table/view DDL and read/write, CREATE/ALTER USER, CREATE/ALTER SETTINGS PROFILE, CREATE/ALTER ROW POLICY, SELECT WITH GRANT OPTION on the four Logbird tables, SHOW ACCESS/GRANTS and system.users/settings visibility. Use ClickHouse 26.9 with SQL_ settings. Provisioning checks credentials, four SELECT grants, effective limits and unchanged main-user row counts. Stop writes during upgrades; concurrent ingest can fail that safety check.

Redis 7 is default. Dragonfly requires `--cluster_mode=emulated --lock_on_hashtags=true`, matching brace-enclosed BullMQ prefixes such as {logbird} across producers/workers, and no queue eviction. Do not use ioredis keyPrefix.

## Upgrades and backups

1. Block browser/SDK ingress and run `docker compose stop app server worker`.
   The worker has a five-minute grace period to finish its current job; wait for
   stop to complete and inspect logs if it needed a forced kill.
2. Take the matched stopped-writer backups below; preserve the original env.
3. Record `git rev-parse HEAD` and `docker compose images` with the backup receipt.
4. Fetch/select the tested revision: `git fetch origin`, then
   `git switch --detach <tested-sha>`. Preserve local changes first.
5. Re-run `sh scripts/selfhost-init.sh` (it preserves existing values and warns if
   `.env` still pins the old `LOGBIRD_IMAGE_REGISTRY=logbird` namespace; remove that
   line so the default `ghcr.io/joodlab` applies). Set LOGBIRD_VERSION to the tested
   release, run `docker compose pull`, then `docker compose up -d --no-build`.
   One-shot migrate gates new API/worker startup; failure blocks startup.
6. Verify readiness, SMTP login, retained events/settings/keys and retention
   receipts before reopening ingress. After a failed receipt the next successful
   run rebuilds that project's rollups and can be expensive. Inspect failed
   receipts and `retention.run_failed` logs after upgrading.

Use the active installation's env/project/override/TLS flags on every command;
a restored project keeps the identity recorded in Cut over below. Query
credentials and database passwords are preserved. Follow the namespace migration
below for older Trailmark installations.

See the [maintainer migration-cancellation check](releases.md#migration-cancellation-check)
for signal handling; its live acceptance is pending in #77.

### Upgrading to immutable ids

Back up Postgres and ClickHouse, preserve the private environment file and stop
server/worker writers; pull and start as in step 5 above. The migrate gate applies
006–009, the receipt/UTC migrations and the additive maintenance-kind and generation migrations.
008 makes a temporary derived-index copy: allow disk space for both copies and
time proportional to retained history. Migration/maintenance clients use a
15-minute socket-idle timeout, progress headers and a ten-minute server query
budget. A failed pre-swap copy is discarded and copied again on retry; after the
atomic swap, retries resume forward without swapping back. Do not start the new
server until the migration gate completes. Restore checks must reject leftover
`event_ids_v2`/`event_ids_v3` tables or temporary MVs, even if the stable table exists.
009 adds an online pointer bloom index and materializes index files; it preserves
logical rows and existing binaries. `MATERIALIZE INDEX` is a mutation proportional
to `event_ids` size (604 ms in the isolated 10M online proof); budget more time for
larger/busy installations. The maintenance migrate client's long timeout covers
this wait. Confirm completion in `system.mutations`; materialization can be repeated safely.
Lightweight runtime purges reuse Wide history bloom files. Physical rewrites and
merges pay the index-build cost: a controlled 10M physical DELETE measured
2.283 seconds without bloom versus 2.741 seconds with it (+458 ms, about 20%),
including 324 ms of bloom calculation. This is a measured example, not a duration
bound; see the [maintenance comparison](ingest-identity.md#multiple-active-parts-009).
External ClickHouse writers need SELECT/INSERT/DELETE on `event_ids` and
`GRANT SYSTEM FLUSH ASYNC INSERT QUEUE ON *.* TO <writer>` in addition to existing
grants. Recovery currently supports one ClickHouse node; a load-balanced cluster
needs a coordinated per-node drain. The worker probes the flush grant at startup.
See the [targeted rollback](ingest-identity.md#deployment-rollback-and-proof-limits).
Replace `logbird` in example SQL with your configured `CLICKHOUSE_DATABASE`.

### Native backup and fresh-storage restore

These shell blocks use POSIX sh (Linux/macOS or Git Bash on Windows). Use
`docker compose cp` for binary archives; PowerShell 5 binary redirection can
corrupt them. These commands assume bundled data services; external database
operators should use their provider's matched backup/restore procedure.

Block browser/SDK ingress, then stop and drain writers before either backup:

```sh
docker compose stop app server worker
docker compose -f docker-compose.yml -f docker-compose.backup.yml up -d clickhouse
mkdir -p .tmp/backups
BACKUP_ID="logbird-$(date -u +%Y%m%dT%H%M%SZ)"
docker compose exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc -f /tmp/logbird.pg.dump'
docker compose cp postgres:/tmp/logbird.pg.dump ".tmp/backups/$BACKUP_ID.pg.dump"
cat > .tmp/backups/backup.sql <<SQL
BACKUP DATABASE logbird TO Disk('backups', '$BACKUP_ID.zip');
SQL
docker compose cp .tmp/backups/backup.sql clickhouse:/tmp/logbird-backup.sql
docker compose exec -T clickhouse sh -c 'clickhouse-client --user "$CLICKHOUSE_USER" --password "$CLICKHOUSE_PASSWORD" --queries-file /tmp/logbird-backup.sql'
```

Require `BACKUP_CREATED` from the synchronous ClickHouse command, then export it:

```sh
docker compose cp "clickhouse:/var/lib/clickhouse/backups/$BACKUP_ID.zip" ".tmp/backups/$BACKUP_ID.zip"
(cd .tmp/backups && sha256sum "$BACKUP_ID.pg.dump" "$BACKUP_ID.zip" > "$BACKUP_ID.sha256")
```

Use a new BACKUP_ID each time; ClickHouse refuses to overwrite an archive. Record
checksums, Git revision, database versions and logical totals: `count()` for
`events`, `sum(events)` for `events_by_minute` and `entities`, and `sum(count)` for
`attribute_keys`. Physical rollup counts change during merges. Copy the matched
archives, checksum file and original env securely off-host. Run
`sha256sum -c "$BACKUP_ID.sha256"` from the off-host archive directory before
deleting any copy. Host archives stay under `.tmp/backups/`, excluded
from Git/Docker; legacy `/backups/` and dump/zip files are also excluded.

Use the [logical-totals query](#recovery-gate-with-ingress-blocked) to record the
backup totals, using the current installation's env/project flags with its copy
and client commands. Save the result beside the matched backup receipt.

After verifying the off-host copy, remove only this archive from the data volume:

```sh
docker compose exec -T -e BACKUP_ID="$BACKUP_ID" clickhouse sh -c 'rm -- "/var/lib/clickhouse/backups/$BACKUP_ID.zip"'
docker compose exec -T postgres rm -- /tmp/logbird.pg.dump
```

For backup only, resume with `docker compose up -d --no-build server worker app`, verify
readiness/login/readback/retention, then reopen ingress. Include usual TLS and
override flags. For an upgrade, keep writers stopped and continue its ordered steps.

Restore into a **different, empty Compose project**, retaining the stopped original
as recovery. Copy its configuration privately to `.env.restore`; retain all
secrets, set `LOGBIRD_BIND=127.0.0.1`, and choose an unused `LOGBIRD_HTTP_PORT` with
matching temporary `APP_URL`. Keep ingress blocked and app/Caddy stopped. Select
the saved BACKUP_ID; do not generate a new timestamp. Verify the saved hashes.
Start only data services; do not run migrations yet.

On **any host**, confirm `git rev-parse HEAD` equals the recorded revision and
`docker compose images` (with the original installation's env/project flags)
matches the backup receipt's image IDs. Source `:local` role tags are shared with the
stopped original project, not scoped by Compose project name; also confirm their
current IDs with `docker image inspect --format '{{.Id}}' logbird-source/migrate:local logbird-source/server:local logbird-source/worker:local logbird-source/app:local`
(substitute the exact recorded image names). Receipts recorded before this release may
use `ghcr.io/joodlab/logbird-<role>:local`; receipts before 2026-11-08 use
the old names `<registry>/<role>:<version>`, for example `logbird/migrate:local`;
inspect those names for such a receipt. If the revision or image identity
does not match or cannot be verified, for example after a failed upgrade, run
`git switch --detach <recorded-git-sha>` and rebuild all four roles sequentially
with the source override and restored env/project flags, before any `up --no-build`.
For published images, pull the exact recorded version and verify its digests instead.

On a replacement host, first make an authorized checkout at the recorded Git
revision. Place the preserved private configuration in `.env.restore` there, copy
the matched `.pg.dump`, `.zip` and `.sha256` into `.tmp/backups/` (create it first), and
pull the four recorded release images before the gate's `up --no-build`
(or build with the source override if the receipt describes a source install). Do not run the quickstart's
startup command against the empty target:

```sh
git clone https://github.com/joodlab/logbird.git
cd logbird
git switch --detach <recorded-git-sha>
# Place .env.restore here and the matched archives/checksum in .tmp/backups/, then:
docker compose --env-file .env.restore -p logbird-restore -f docker-compose.yml -f docker-compose.backup.yml pull migrate
docker compose --env-file .env.restore -p logbird-restore -f docker-compose.yml -f docker-compose.backup.yml pull server
docker compose --env-file .env.restore -p logbird-restore -f docker-compose.yml -f docker-compose.backup.yml pull worker
docker compose --env-file .env.restore -p logbird-restore -f docker-compose.yml -f docker-compose.backup.yml pull app
```

Then restore the matched data into the empty services:

```sh
BACKUP_ID=logbird-20261107T120000Z # replace with the saved backup ID
(cd .tmp/backups && sha256sum -c "$BACKUP_ID.sha256")
docker compose --env-file .env.restore -p logbird-restore -f docker-compose.yml -f docker-compose.backup.yml up -d --wait postgres clickhouse redis
docker compose --env-file .env.restore -p logbird-restore cp ".tmp/backups/$BACKUP_ID.pg.dump" postgres:/tmp/logbird.pg.dump
```

### Normalize restored ClickHouse parts

**Normalize after every native ClickHouse restore before starting writers.** The
pinned ClickHouse 26.9.27.3 can restore parts with mutation versions higher than
new delete mutations. A mutation may report success while rows remain. The source
guard checks deletion and raises `LOGBIRD_DELETE_INCOMPLETE` before reinsertion.
Transient [concurrent-mutation skips](https://github.com/ClickHouse/ClickHouse/pull/124167)
are retried automatically with a fresh DELETE, up to three total attempts (logged as
`clickhouse.delete_retry`). If the error still appears, retry the operation (retention
runs again on its own). Only a failure that persists on a natively restored database
needs the normalization procedure below. Every verified delete that fails closed (worker
retention and repair, API sample-data removal and project deletion, `demo-clean`) logs one
`clickhouse.delete_incomplete` line with the table and project; the API answers 503 with
`Retry-After`. If storage fails after a DELETE ran (the verification probe times out, or a
retry DELETE errors), the delete is unproven: it fails closed as `LOGBIRD_DELETE_UNVERIFIED`,
logs `clickhouse.delete_unverified`, and gets the same retryable 503. The non-fatal stale-pointer cleanup logs only its own warning: ingest
recovery or sample-data removal logs `clickhouse.event_index_stale_pointers` when it cannot
delete stale identity pointers.
The pinned 26.9 line has no upstream fix for that race; ClickHouse 26.10 and later include it.
Moving the pin is tracked in [#147](https://github.com/joodlab/logbird/issues/147).
**Live verification of the packaged guard and retry after normalization is pending
in [#77](https://github.com/joodlab/logbird/issues/77); full DR readiness is not
claimed.** See [#75](https://github.com/joodlab/logbird/issues/75).

The receipt table is Prisma's `"RetentionRun"`. Wait until each restored project's
latest run is `completed`, started after GATE_STARTED, and the missing count is
zero. A running receipt needs more time; a failure or guard log blocks cutover. So does
`clickhouse.event_index_stale_pointers`: stale identity pointers remain and need investigation
(ineffective normalization is one possible cause, repeated concurrent-mutation skips another).
A `clickhouse.delete_retry` during the gate does not block by itself, because a retry can
also succeed on a restored part that only slightly outranks the new mutations. Whether or not
it logged, run the version check below before cutover. In a non-replicated MergeTree, inserts
and mutations share one block counter, so it compares only *mutated* parts
(`data_version > min_block_number`; a part that was never mutated, merged or not, has
`data_version = min_block_number`) with the newest mutation each table received during the
gate. A table that has mutated parts but received no gate mutation (for example because no
restored row had expired yet) cannot be checked this way, so it also reports
`blocks_cutover = 1`. Only finished gate mutations count: `pending_gate_mutations` shows
how many are still running, so wait for them (or treat a stuck one as blocking). No output means none of the five tables that deletes touch has mutated parts. The check assumes a
restored part can outrank new mutations only through its mutation version, as observed so
far; the mandatory normalization (`TRUNCATE` + `INSERT`) removes the case entirely, and live
verification of restored parts is tracked in [#77](https://github.com/joodlab/logbird/issues/77).

```sh
cat > .tmp/backups/mutation-versions.sql <<SQL
SELECT p.table,
       max(p.data_version) AS mutated_part_version,
       any(m.done_version) AS newest_gate_mutation,
       ifNull(any(m.pending), 0) AS pending_gate_mutations,
       newest_gate_mutation IS NULL OR mutated_part_version > newest_gate_mutation AS blocks_cutover
FROM (SELECT table, data_version FROM system.parts
      WHERE database = 'logbird' AND active AND data_version > min_block_number
        AND table IN ('events', 'event_ids', 'events_by_minute', 'entities', 'attribute_keys')) p
LEFT JOIN (SELECT table,
                  maxIfOrNull(toUInt64(extract(mutation_id, '(\d+)')), is_done) AS done_version,
                  countIf(NOT is_done) AS pending
           FROM system.mutations
           WHERE database = 'logbird' AND create_time >= parseDateTimeBestEffort('$GATE_STARTED')
           GROUP BY table) m ON m.table = p.table
GROUP BY p.table
ORDER BY p.table
SETTINGS join_use_nulls = 1
SQL
docker compose --env-file .env.restore -p logbird-restore cp .tmp/backups/mutation-versions.sql clickhouse:/tmp/mutation-versions.sql
docker compose --env-file .env.restore -p logbird-restore exec -T clickhouse sh -c 'clickhouse-client --user "$CLICKHOUSE_USER" --password "$CLICKHOUSE_PASSWORD" --queries-file /tmp/mutation-versions.sql'
```

## Sizing

The bounded 2026-11-07 evaluation observed about 14.7 GB for images plus private
build cache and a 1.79 GB migrate image (historical images at 1a62ff4). This is an
observation, not a disk requirement or capacity guarantee. Reserve additional
space for raw data, backup archives, merge headroom and a full restore staging
table. Build roles sequentially by default; an 8 GB runtime allocation does not
establish that concurrent source builds will fit.

Start a bounded evaluation with 4 vCPU, 8 GB RAM and SSD. This is an initial allocation, not measured capacity. Reserve RAM/disk for ClickHouse merges/backups and measure compressed growth with fictional representative traffic. Monitor disk, readiness, 5xx/429, queue age, retention failures and backup age. One VM has no HA. See [deployment](deployment.md) and [Coolify](coolify.md).

Record `docker stats --no-stream`, `docker system df` and host free memory before
startup, at idle and during a stated workload. Image sizes and build cache are
separate from retained event storage; keep space for both during upgrades. Review
`docker compose logs --since 10m server worker migrate` for migration completion,
`worker.ready`, request errors and retention results. Code logging must be disabled
before collecting or sharing logs. `/readyz` is a dependency check; it does not
prove SMTP, successful retention, backup freshness or spare capacity. There is no
bundled metrics collector or Prometheus endpoint; configure external host/Docker
monitoring and alerts. See [releases](releases.md) for architecture and
image-publishing gates.

Retention-heavy installations also need background mutation capacity. ClickHouse
merges and mutations share `background_pool_size`; a very small pool (for example,
two threads) can leave lightweight deletes waiting behind concurrent purges. Inspect
`system.mutations`, `system.merges`, retention completion time and disk/CPU pressure.
Review `background_merges_mutations_concurrency_ratio` and
`number_of_free_entries_in_pool_to_execute_mutation` together before changing the
pool: a larger pool consumes resources, and incompatible mutation thresholds can
prevent progress. Benchmark representative retention alongside ingestion rather
than copying a shared development server's settings or extrapolating its purge
latency to production. See the [ClickHouse background-pool reference](https://clickhouse.com/docs/reference/settings/server-settings/settings/background#background_pool_size).

With 009, distinguish lightweight deletes from physical rewrites. The runtime's
lightweight retention reused its Wide history bloom files (538 ms versus 503 ms
of part work without/with bloom on a controlled 10M fixture, no bloom calculation).
Tiny affected Compact parts may rebuild their small index. Physical ALTER DELETE
and merges rebuild index files as they rewrite data; the same fixture's physical
delete took 2.283 versus 2.741 seconds, including 324 ms of bloom calculation.
Budget and monitor that index cost alongside disk and merge work rather than
attributing all synchronous DELETE latency to index calculation.

Receipt expiry has its own `ingest-receipts` queue, separate from ClickHouse
retention. Keep the worker running: it schedules a globally single-flight sweep
every minute, in 5000-row batches with 10 ms yields and a 20-second work budget.
The last batch is additionally bounded by a five-second SQL timeout and a
six-second transaction/one-second connection wait. Its timeout and
`enable_bitmapscan=off` are transaction-local (SET LOCAL semantics), not shared
Postgres settings; the planner setting keeps ordered expiry scans on the existing
indexes when statistics are stale. The hourly sweep remains a backstop.

At an aggregate 5000 receipts/second, sustained cleanup must exceed 300000/minute
(more than 15000/second while the 20-second worker budget runs). With healthy
on-time scheduling, budget roughly three million live-cache rows plus at most
450000 expired rows. This does not cap physical disk usage; watch autovacuum,
dead tuples, WAL, queue lag and `ingest.receipts_pruned` logs, especially repeated
`limited` results or `ingest.receipt_sweep_failed`. A worker outage adds roughly
300000 expired rows per minute at that rate, without a hard bound. An hourly-only
backstop can accumulate about 18 million between successful sweeps. Requests
expire only their own requested ids in a bounded statement; fresh batches never
drain unrelated backlog. See [receipt coordination](ingest-identity.md#coordination-and-identity).

## Upgrading from the previous namespace

Existing installations need an explicit, offline namespace migration before running
this version. Do not point the new code at empty databases beside existing data.
The script requires the old administrator connection settings and reuses
`CLICKHOUSE_QUERY_PASSWORD`; it never generates or prints replacement credentials.
Use `MIGRATION_DATABASE_URL` for a PostgreSQL administrator distinct from the old
application role (connected to `postgres`). PostgreSQL cannot rename the session
user. A database rename requires every other connection to be closed; the script
lists blockers and refuses rather than terminating them.

1. Stop ingress, console, server, workers and every other database client, including
   development instances. Drain in-flight jobs. Take PostgreSQL `pg_dump` plus globals,
   a ClickHouse backup including access metadata, and a Redis snapshot; verify restore
   into a separate instance. Preserve `.env`, passwords and the migration journal.
2. From the repository root with the old `.env` still in place:

   ```sh
   node --env-file=.env --import tsx scripts/migrate-namespace-to-logbird.ts --dry-run
   node --env-file=.env --import tsx scripts/migrate-namespace-to-logbird.ts --yes
   ```

   `--include-local-fixtures` opts into changing only fixture email suffixes.
   `--drop-old-redis-keys` opts into scanning/deleting only the exact old queue prefix.
   Omit both by default. No Redis flush is used. The dry run inspects prerequisites
   and prints the plan without writes. `.tmp/namespace-migration.json` records object
   definitions and pre-move physical table counts; keep it with the backups. On
   interrupted runs, retain that journal and rerun with all writers still stopped.
   The completed journal is archived with a `.completed` suffix. Materialized views
   are moved and rebound from their captured definitions; their destination tables
   carry the verified row counts. Source payload JSON remains original audit evidence.
3. Apply the printed environment name changes. Set Postgres database/user to `logbird`,
   ClickHouse database to `logbird`, restricted user to `logbird_query`, queue prefix
   to `{logbird}`, and rename branded environment keys to `LOGBIRD_*`. Keep passwords.
   A server-configured ClickHouse administrator (XML/environment configuration) must
   be renamed in that configuration using the same password; the migration does not
   rewrite server configuration. SQL access objects for restricted reads are rebuilt
   by the shared provisioning helper, then old policies/user/profile are removed.
4. Start database services with the updated identity configuration, deploy schema
   migrations, then start the Logbird server, worker and console. Confirm old stored
   API keys still ingest, new keys start with `lb_`, projects/users/events and derived
   counts match, cross-project reads remain denied, and retention completes on the new
   queue. Users sign in again; browser preferences start fresh.

If an in-place PostgreSQL rename is unavailable, restore `pg_dump` into `logbird`
using a separately provisioned `logbird` role with the existing password and ownership.
Verify counts, constraints, sequences and stored API-key hashes before switching;
keep the original database offline as recovery until acceptance. Do not run the
rename tool against two populated PostgreSQL namespaces. On failure keep writes
stopped and investigate with the journal; recover all three stores from the same
backup boundary rather than mixing old and new writes. The script is offline and
idempotent, not a distributed transaction or an online migration.

## Ingest insert settings

Every ingest INSERT pins `async_insert_max_data_size=67108864` (64 MiB),
`min_insert_block_size_bytes=268402944`, `min_insert_block_size_rows=1048449`,
`max_insert_block_size=1048449`, `input_format_allow_errors_num=0` and
`input_format_allow_errors_ratio=0` at query level, together with
`async_insert=1` and `wait_for_async_insert=1`. The 5 MiB request limit does not
bound the normalized statement to 5 MiB: duplicated changes and the escaped payload
expand it, to about 15 MiB in the worst realistic case. These are thresholds, not
preallocated buffers. Row/block pins keep a statement in one block if ClickHouse
falls back to synchronous insertion, which otherwise can partially write before a
late parser failure (measured on 26.9: 2300 of 3000 rows written with small blocks).
Ingest splits cached rows into consecutive statements of at most 64 MiB, sharing
the statement, byte, clock and lease budgets across chunks. A single row larger than
64 MiB stays alone; its parse error is ambiguous and reconciled by recovery.
This remains possible with extreme attribute paths until the size bound in #159 lands.
The two error-tolerance pins prevent operator profiles from silently skipping bad
rows while acknowledging success, which would lose those events.

Query-level pins win over ordinary user profiles. Operators should allow these
settings for the writer and avoid server constraints that reject them. ClickHouse
rejects the entire query with code 452 (`SETTING_CONSTRAINT_VIOLATION`) before
reading data if a pin violates a constraint; ingest returns retryable
`503 ingest_unavailable` and releases the unwritten claims. A parse code is isolated only
when the serialized body fits the pinned async limit, its error names
`WaitForAsyncInsert`, and it is not a materialized-view failure: "while pushing to view" doesn't
appear in it, and neither does a view name (one of Logbird's nine views, or any
`database.name_mv`) that is absent from the statement body. ClickHouse quotes the offending
input verbatim, so row values such as `'page.view'` or `'analytics.events_by_minute_mv'` don't count.
If a ClickHouse upgrade changes the `WaitForAsyncInsert` wording, parse failures
become ambiguous and can loop through pending/recovery until the incompatibility is fixed.
Do not infer pre-write safety from the
parse code alone. No new migration or settings profile is needed.

Exact-row isolation assumes `(at row N)` is statement-relative and 1-based,
including when multiple bodies share an async flush. The shared-flush test in
`apps/server/src/ingest-parse-isolation.integration.test.ts` verifies this on
ClickHouse 26.9. Other versions must retain that behavior; run the test after
every ClickHouse upgrade before accepting ingest traffic; it also checks the async error wording.

## Webhook endpoint settings

The endpoint management API can store and rotate secrets; this change does not
send webhooks yet. Each project may have up to 10 endpoints. Owners and admins
manage them; workspace members can read endpoint configuration without secrets.
Create and rotate return a `whsec_` secret once, with `Cache-Control: no-store`.
Save it in the receiver's secret store. Never put it in a webhook URL.

Secrets use AES-256-GCM encryption. By default the key is derived with HKDF-SHA256
from `BETTER_AUTH_SECRET` (info `logbird-webhook-secrets-v1`). No new setting is
required. Optionally set `WEBHOOK_SECRET_KEY` to the base64 encoding of 32 random
bytes, consistently on the server and worker. This keeps the encryption key
independent of auth-secret rotation. Both Compose variants pass this optional key
and `BETTER_AUTH_SECRET` through the shared runtime environment to both roles.

Changing `BETTER_AUTH_SECRET` without a stable `WEBHOOK_SECRET_KEY` makes existing
webhook secrets unreadable: rotate each endpoint's webhook secret too and update
its receiver, using `overlapSeconds: 0` to expire unreadable old secrets
immediately. The old overlap secrets cannot be decrypted with the new key.
Changing `WEBHOOK_SECRET_KEY` likewise requires rotating the webhook secrets.
The versioned ciphertext envelope alone does not provide a keyring or automatic
key migration.

URLs require HTTPS. `WEBHOOKS_ALLOW_HTTP=true` explicitly permits HTTP for
self-hosted receivers, but still requires public unicast addresses. Loopback,
private, link-local, CGNAT, multicast, unspecified, reserved, documentation and
metadata addresses are rejected, including mapped/translated forms. Every DNS
answer must pass validation. Credentials and fragments are forbidden. Save-time
validation does not protect a sender against DNS rebinding; the future sender
must resolve and pin an allowed address again when connecting.

PATCH `scope` replaces the whole scope; `null` clears it. `filterQuery` uses the
Logbird query language (empty matches everything). Secret rotation accepts an
`overlapSeconds` integer from 0 to 604800 (default 86400); omitted fields in PATCH
remain unchanged. Delivery, filters at delivery time, retries and the UI arrive
in later webhook PRs.
