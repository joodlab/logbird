Security
How Logbird handles your data.
An audit log holds sensitive history, so this page says what Logbird does with it and where each protection stops.

Where data lives
Self-hosted, your events stay on your servers.
When you self-host, events are stored in your own ClickHouse, and workspaces, projects and keys in your own Postgres. The self-hosted software doesn't send usage data back to us. In the bundled deployment, the server connects out to the SMTP provider you choose and, when you add webhook endpoints, delivers events to them; it resolves an endpoint's hostname when you save it and before each delivery.

[aria-hidden] sign-in codes, invitations
Your SMTP provider
The bundled Compose deployment: the console, API, worker, Postgres, ClickHouse and Redis all run on your server. Outbound, the server connects to your SMTP provider (sign-in codes, invitations and membership notices) and delivers webhooks to the endpoints you add, looking up each endpoint's hostname when you save it and before each delivery. With your own databases, it also connects to them.
Retention
Expired events are permanently deleted.
Each project has a retention window, from 7 days to 10 years. New projects start at 90 days.
A worker deletes events older than the window every hour. Each run is recorded and shown in Settings.
Before you lower retention, Logbird shows roughly how many events it will delete. To confirm, you type the project's slug. The purge starts right away.
Deleting a project deletes all of its events.
There's no archive and no undo.
Projects and keys
Every key belongs to one project and does one job.
[aria-hidden: ]
Project-bound keys
An API key works for exactly one project.
[aria-hidden: ]
Two kinds
Ingest keys (lb_ingest_...) can only write. Read keys (lb_read_...) can only read.
[aria-hidden: ]
Stored hashed
Logbird keeps a SHA-256 hash and a short display prefix. The full key is shown once, when you create it.
[aria-hidden: ]
Revocable
Revoke a key in Settings; the console shows when each key was last used.
[aria-hidden: ]
Workspace boundaries
The server checks on every request that the project belongs to your active workspace. A request for another workspace's project gets a 404 and reveals nothing about it.
Scoped reads: one customer account per key or token.
[aria-hidden: ]
One account per scope
One customer account per scope, matched on the id Logbird stored.
[aria-hidden: ]
Two layers
Logbird's query builders always apply the scope. ClickHouse checks the customer account as well once the restricted query user has its tenant row policy: the Compose and Coolify stacks install it on upgrade, and a source installation runs create-query-user once.
[aria-hidden: ]
Browser origins
A web page on another origin can read with a token only if that origin is listed on the key.
Webhook endpoints: signed, checked, and managed by admins.
[aria-hidden: ]
Owners and admins only
Only owners and admins can see or manage webhook endpoints: a stored URL can itself be a credential.
[aria-hidden: ]
Secrets shown once
Each endpoint's signing secret is encrypted at rest (AES-256-GCM) and shown once, when you create or rotate it.
[aria-hidden: ]
Public destinations only
A destination must resolve only to public addresses. Logbird checks it when you save the URL and again before every delivery, and connects only to the address it checked.
[aria-hidden: ]
No redirects, no console credentials
Redirects are never followed: a redirect counts as a failed attempt, retried while the 24-hour window is open. A delivery carries the event and its signature headers, never console headers or cookies.
[aria-hidden: ]
Masks on every delivery
Field masks set on an endpoint apply to every delivery, including retries and resends.
SQL mode
SQL search that can only read your project.
SQL mode accepts a single boolean WHERE expression. Four layers stand between it and other people's data.
[aria-hidden] 1
Checked against ClickHouse's own parse
The server asks ClickHouse for the statement's syntax tree. It rejects anything that isn't exactly Logbird's own query with your condition in it.
[aria-hidden] 2
Allowlisted
Only known columns and a fixed list of functions may appear. Subqueries, UNION, WITH, SETTINGS, table functions, system tables, comments and semicolons are rejected.
[aria-hidden] 3
A restricted user
Queries run as a separate read-only ClickHouse user. It can only SELECT, and it has fixed ceilings on time, rows read, memory and result size.
[aria-hidden] 4
Row policies
Database row policies limit that user to the project you're authorized for. Even 1 OR 1 can't return another project's rows.
Where these layers stop
These layers protect against a broadened or malformed filter. They don't replace the server's own authorization, and they don't protect against stolen database credentials. SQL mode is for the console only; the public API rejects it.
Roles
Permissions are checked by the server.
Owners and admins manage projects, keys, retention and invitations. Members search, export, save views and read workspace activity. Any action that isn't explicitly allowed is denied, for every role. The UI hides what you can't do, but the API is what enforces it.
One-time sign-in codes
Sign-in is by a one-time code sent by email. There are no passwords to leak.
Rate-limited sign-in
Sign-in requests are rate-limited per client.
Impersonation
When staff act for a customer, both names are recorded.
Send the staff member as impersonator and keep the customer as actor. The event detail shows both. Search impersonator:* to list every event done on someone's behalf. In the console, those rows are marked "via support", the "Done by support" filter lists them, and each support agent has a page with everything they did while signed in as a customer.

Workspace activity
Logbird records its own management actions.
Logbird records management actions (projects, keys, retention, invitations) in workspace activity. Every member can read it.

Rate limits and delivery
Bounded by design.
Each project has its own ingest and read rate limits, shared across replicas through Redis.
Failed authentication attempts are limited per client, so repeated bad keys are throttled. Valid keys keep working behind a shared network address.
If Redis fails, sign-in limits fail closed (requests are refused) and ingest and read limits fail open (requests continue).
Delivery is at least once when the client retries unsettled events, as the SDK does. An exact retry with the same valid, non-blank string id reuses the stored event while the project retains it, so retries from the SDK, which sets ids, don't add copies; changed content under that id is rejected with duplicate_id_conflict. An event sent without an id gets a new one on every retry. Once retention deletes an event, its id can be used again.
Don't send secrets. The SDK's redact() helper replaces common secret fields before sending.
Responsible disclosure
Report a vulnerability privately.
Please don't post details in a public issue. Email security@example.test. Include the affected version, a reproduction using fictional data, and the impact. We'll coordinate the fix and the disclosure with you. We don't offer a response-time SLA yet.
Email security@example.test
What we don't claim
No certifications yet.
Logbird doesn't hold SOC 2, ISO 27001 or any other certification today, and we don't claim that using it makes you compliant with any law or standard. Logbird can help you answer an auditor's questions: who did what, when, in which account, and what changed. The rest of the work is yours, and we'll say so plainly.
