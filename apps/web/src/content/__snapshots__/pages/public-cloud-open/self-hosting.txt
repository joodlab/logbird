Self-hosting
Your audit log, on your servers.
Logbird is MIT-licensed and self-hosts with Docker Compose. Run it on one VM and your events stay on your own servers. It's the same codebase Logbird Cloud runs.

[sr-only] One Compose project runs the console, API, worker, Postgres, ClickHouse and Redis.
Compose pulls the published 0.2.1 images for amd64 and arm64 from GHCR.
Quickstart
From clone to your first event.
You need Docker Engine and Docker Compose 2.24.4 or newer. Compose pulls the four published Logbird role images; nothing is compiled on your server.
[aria-hidden] 1
Open http://localhost:4600 and sign in with the code sent to your email, or printed in the server log if you set AUTH_LOG_SIGN_IN_CODES=true.
[aria-hidden] 2
Create a workspace and a project. Copy the ingest key; it's shown once.
[aria-hidden] 3
Set LOGBIRD_INGEST_KEY to the key you just copied, and send an event with the request on the right.
[aria-hidden] 4
Expect 202, and the event in the explorer.
The init script generates the secrets it needs and never overwrites values you've set.
Need unreleased code or a custom build? The self-hosting guide covers building from source, every setting, TLS, backups and restores.
/livez checks the API process; /readyz checks Postgres, ClickHouse and Redis.
On your server
pre| git clone --branch v0.2.1 https://github.com/example-org/logbird.git logbird
pre| cd logbird
pre| sh scripts/selfhost-init.sh   # creates .env and generates secrets
pre| # Set SMTP in .env, or AUTH_LOG_SIGN_IN_CODES=true for a first local test.
pre| # Internet-facing? Also set AUTH_SIGNUP=restricted and AUTH_SIGNUP_DOMAINS.
pre| docker compose pull
pre| docker compose up -d --no-build
Your first event
pre| curl http://localhost:4600/v1/events \
pre|   -H "Authorization: Bearer $LOGBIRD_INGEST_KEY" \
pre|   -H 'Content-Type: application/json' \
pre|   -d '{"action":"document.updated"}'
Requirements
What you need.
Host
A Linux host, or any machine that runs Linux containers, with Docker Engine and Compose 2.24.4 or newer.
Email
An SMTP provider for sign-in codes and invitations, for example Amazon SES, Postmark or Brevo.
HTTPS
A domain and ports 80 and 443 if you want automatic HTTPS.
Starting size
4 vCPU, 8 GB RAM and SSD storage. That is an initial allocation, not measured capacity. Leave disk for images as well as your data, ClickHouse merges and backups; building from source needs more headroom still.
Access
Sign-up is open by default: anyone who can reach the console can create an account. On an internet-facing instance, set AUTH_SIGNUP=restricted with your email domains; invitations keep working.

[sr-only] Your product sends events to the Logbird API, which writes them to ClickHouse. The console and the read API read from ClickHouse. Postgres stores workspaces, projects and hashed keys. A retention worker deletes expired events every hour.

Bundled Compose
One Compose project runs Postgres, ClickHouse, Redis, the API, the worker and the console. Only the console port is published, on 127.0.0.1 by default. A one-off migration step runs before the API and worker start.

[sr-only] Logbird services in Compose, databases you run
Bring your own databases
Use your own Postgres, ClickHouse and Redis (or Dragonfly) with docker-compose.external.yml. Use ClickHouse 26.9. Logbird creates its own restricted query user and row policies.
Step by step in the Coolify guide. Upgrades and restores through Coolify are documented but not yet verified end to end.
HTTPS
Automatic HTTPS, or the proxy you already run.
Set your domain in .env and run docker compose --profile tls up -d. Caddy gets and renews the certificate. Already run Nginx, Traefik or another proxy? Forward the whole origin to port 4600 and tell Logbird how many proxies sit in front, so rate limits and audit context see the real client address.
Never expose the API server's own port. Everything goes through the console origin.
Caddy, built in
pre| # .env
pre| APP_URL=https://audit.example.com
pre| LOGBIRD_DOMAIN=audit.example.com
pre| TRUST_PROXY=2
pre|
pre| docker compose --profile tls up -d
[sr-only] Operating Logbird
Email
Sign-in is by emailed code.
Logbird has no passwords. People sign in with a one-time code sent by email, so configure an SMTP provider. For a first local test you can log sign-in codes to the server log instead. Turn that off once SMTP works: anyone who can read the logs can sign in.
Upgrades and backups
Upgrade to a pinned release, after a backup.
[aria-hidden] 1
Stop writes
Run every command in these steps with the installation's own Compose project, env file, -f files and profile (after a restore cutover, the restored project's). Block ingress and stop the console, server and worker. The worker gets five minutes to finish its current job: wait for the stop to complete, and check its logs if it had to be killed.
[aria-hidden] 2
Back up
With writers stopped: matched Postgres (pg_dump) and ClickHouse (BACKUP DATABASE) backups and a SHA-256 checksum file. Keep the original env file; record the Git revision (git rev-parse HEAD) and the images (docker compose images).
[aria-hidden] 3
Pin the new version
Check out the release tag vX.Y.Z, then set LOGBIRD_VERSION=X.Y.Z, without the v, in the env file the installation runs with (.env, or the one you cut over to after a restore): its value overrides the Compose default, and a LOGBIRD_VERSION or LOGBIRD_IMAGE_REGISTRY exported in your shell overrides the env file (unset it). Run docker compose config --images and check the full names: all four must be <registry>/logbird-<role>:X.Y.Z, with the registry you expect (the project's GHCR namespace by default). Built from source (docker-compose.build.yml)? Keep that override and build the four roles from the new revision instead; the image check doesn't apply.
[aria-hidden] 4
Pull, then start
docker compose pull (skip it for a source build), then docker compose up -d --no-build. Migrations run first; if one fails, the new version doesn't start.
[aria-hidden] 5
Verify
Readiness, sign-in, your events, settings and keys, and the retention runs, before you reopen ingress.
docker compose down keeps your data. docker compose down -v permanently deletes the Compose-managed volumes, which hold the bundled Postgres, ClickHouse and Redis data.
Restore into empty, separate storage first, and check counts before you switch over.
Not there yet
What self-hosting doesn't include today.
High availability
The Compose setup is a single VM. It has no failover.
Production sizing guarantee
There's no published sizing guarantee yet. Size from your own measurements.
SSO
Sign-in is by emailed code only. SSO is on the roadmap.
Rather not run it yourself?
Logbird Cloud runs the same codebase for you. It's in early access, with sign-ups limited to invited teams.
